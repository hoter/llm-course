## Неделя 1 — Первый вызов, логирование и параметры генерации

### 🎯 Цель недели и критерий готовности

**Цель:** получить работающий вызов модели, который решает одну узкую задачу, с полным логированием входа/выхода и пониманием того, как параметры генерации меняют поведение.

**Критерий готовности (Definition of Done):**

- [x] Есть скрипт или минимальный сервис, который делает вызов модели через официальный SDK.
- [x] Для 3–5 вызовов сохранены: полный текст запроса, ответ, usage (количество токенов) и параметры генерации.
- [x] Можно показать два разных ответа на один и тот же запрос при разных `temperature` и объяснить, почему они отличаются.
- [x] Всё, что должно быть точным (числа, статусы), считается в коде, а не «доверяется» тексту модели.

### 🧩 Шаг 1: Выбор задачи (0/5 → 1/5)

Взял задачу из своего домена — **категоризация учебных статей по мифологиям**. На вход идёт текст статьи, на выходе — какая мифология ей соответствует и уверенность модели.

Задача узкая и проверяемая: есть закрытый список из 43 мифологий, у каждой свой `taxonomy_id`. Никакого «чата» — обычная функция: текст на входе, структурированный результат на выходе.

**Почему это лучше чата:** выход сразу проверяем. Модель не пишет эссе, а выбирает значение из фиксированного словаря, которое можно сверить со справочником в коде.

### 🔌 Шаг 2: Прямой вызов через SDK (1/5 → 2/5)

Провайдер — **DeepSeek** через официальный OpenAI SDK (совместимый интерфейс, Responses API). Без LangChain и прочих обёрток — видно «сырой» запрос и «сырой» ответ.

```python
from openai import OpenAI

client = OpenAI(
    api_key=os.getenv("DEEPSEEK_API_KEY"),
    base_url=os.getenv("DEEPSEEK_BASE_URL"),
)

response = client.responses.create(
    model=prompts.MODEL,
    instructions=prompts.PROMPT_INSTRUCTION,
    input=text,
    temperature=prompts.TEMPERATURE,
    text={...},  # JSON Schema для ответа
)
```

Ответ модели ограничен **JSON Schema** (`json_schema`, `strict: true`): модель физически не может вернуть свободный текст — только объект с полями `mythology` и `confidence`.

### 📝 Шаг 3: Логирование входа и токенов (2/5 → 3/5)

Каждый вызов пишется в `logs/calls.json`:

| Поле | Что содержит |
|---|---|
| `timestamp` | время вызова |
| `model`, `temperature` | параметры генерации |
| `instruction` | полный системный промпт (как он реально ушёл в контекст) |
| `prompt` | входной текст статьи |
| `input_tokens`, `output_tokens`, `total_tokens` | usage из ответа |
| `output` | сырой ответ модели |
| `status`, `taxonomy_id` | результат проверки в коде (см. шаг 5) |

Инструкция логируется целиком, а не по частям: в контекстное окно системный промпт и пользовательский ввод попадают одной «склейкой», и без полного лога невозможно потом понять, из-за чего модель ошиблась — из-за плохих данных или из-за случайного мусора в контексте.

Логи не через `print`, а структурно в файл — это первый датасет для разбора ошибок.

### 🌡️ Шаг 4: Эксперименты с параметрами генерации (3/5 → 4/5)

Один и тот же вход прогоняется с разными `temperature`, результаты сводятся в таблицу в [RESULTS.md](RESULTS.md).

Что зафиксировано:

- при низкой температуре (`0.0–0.2`) модель чаще выбирает самый вероятный токен, ответы повторяются и не «фантазируют» с ID;
- при высокой (`0.7–1.0`) распределение «размазывается»: ответ гуляет, вплоть до вариантов, которых нет в списке мифологий;
- `temperature=0` не даёт полного детерминизма — небольшие различия между запусками остаются, и бизнес-логика не должна от них ломаться;
- `max_tokens` для структурированного выхода держится маленьким, чтобы ответ не «растекался мыслью».

Практическое правило, к которому пришёл: `temperature` и `top_p` одновременно не крутить, для этой задачи хватает `temperature`.

### 🔢 Шаг 5: Детерминированные вычисления в коде (4/5 → 5/5)

Модель отвечает только на нечёткий вопрос — «к какой мифологии относится текст». Всё, что имеет единственно правильный ответ, считается в коде:

1. Модель возвращает `mythology` и `confidence`.
2. Код сверяет `mythology` со справочником `prompts.MYTHOLOGIES` и берёт `taxonomy_id` оттуда — не из ответа модели.
3. Если мифологии нет в справочнике → `status = "ERROR"` (модель галлюцинировала).
4. Если `confidence == "low"` → `status = "REVIEW"` (решение уходит на ручную проверку).
5. Иначе → `status = "OK"`.

```python
if output["mythology"] in prompts.MYTHOLOGIES:
    data["taxonomy_id"] = prompts.MYTHOLOGIES[output["mythology"]]
    if output["confidence"] == prompts.MIN_LEVEL:
        data["status"] = "REVIEW"
else:
    data["status"] = "ERROR"
```

Модель даёт суждение, код — точность. Эта граница проводится осознанно: даже если модель «решит», что статья про славянскую мифологию, числовой ID всегда приходит из справочника, а не из текста модели.

### ⚠️ Типичные ловушки первой недели

- **Сразу лезть во фреймворк.** Пропускаешь понимание того, как формируется контекст и как читать usage.
- **Не логировать вход.** Через неделю не воспроизвести ни один проблемный кейс.
- **Путать `max_tokens` и контекстное окно.** `max_tokens` ограничивает выход, контекстное окно — весь запрос (вход + выход). Почти заполненный вход = нет места для ответа.
- **Ожидать полного детерминизма при `temperature=0`.** Его может не быть; система проектируется так, чтобы редкие различия не ломали бизнес-логику (см. шаг 5).

## Запуск

```bash
# 1. Зависимости
pip install openai python-dotenv

# 2. Ключи в .env (файл в репозиторий не попадает)
DEEPSEEK_API_KEY=...
DEEPSEEK_BASE_URL=...

# 3. Запуск
python main.py
```

Скрипт просит текст статьи, делает вызов модели, проверяет ответ и дописывает запись в `logs/calls.json`.

## Настройки генерации

Меняются в `prompts.py`:

| Параметр | Значение | Комментарий |
|---|---|---|
| `MODEL` | `deepseek-flash` | модель провайдера |
| `TEMPERATURE` | `0.2` | для классификации нужна стабильность |
| `MIN_LEVEL` | `low` | порог, ниже которого ответ уходит в `REVIEW` |
